# scareblock

2026-2 데이터사이언스프로젝트 (캡스톤 디자인)

## 개요

**지연 기반 다중 민감 콘텐츠 사전 차단 프레임워크.**

유튜브 영상을 3초 늦게 보여주고, 그 3초 동안 트리거 장면을 찾아 사용자에게 도달하기 전에 가린다.
점프 스케어(jump scare)는 이 구조가 필요한 유일한 카테고리이자 첫 flagship 구현체이고,
프레임워크는 처음부터 여러 카테고리를 겨냥한다.

> **용어** — 논문·발표에서는 구어인 "갑툭튀" 대신 국내 학술 논문에서 통용되는 **점프 스케어**를 쓴다.
> 사용자에게 일어나는 반응은 **놀람 반사**(startle reflex), 계산 문제로는
> **돌발 시청각 사건 탐지**로 부른다. 전체 용어표는 [docs/related-work.md](docs/related-work.md#용어)에 있다.

### 범위 선언

**대상은 유튜브 일반 업로드 VOD로 한정한다.** 영화·대여 등 EME(Widevine)가 걸린 콘텐츠는
**화면 픽셀을 읽을 수 없어** 블러 개입이 불가능하므로 평가셋과 데모에서 제외한다.
이는 구현 미비가 아니라 브라우저 DRM 규격상의 경계다.

실측 결과 차단 방식은 예상과 달랐다(2026.09.08) — `drawImage`가 예외를 던지는 taint가 아니라
**검은 프레임이 그려진다**. 그리고 **오디오는 차단되지 않았다**(RMS 0.0675). 즉 DRM 콘텐츠에서도
오디오 기반 탐지 자체는 가능하며, 막히는 것은 화면 개입이다. 자세한 수치는
[`poc/README.md`](poc/README.md)에 있다.

## 핵심 아이디어

### 1. 지연 버퍼

점프 스케어는 소리와 화면이 동시에 터진다. "지금"을 보고 있으면 이미 늦는다.
화면을 3초 미뤄두면 AI가 먼저 읽을 시간이 생기고, 위험한 구간이 사용자에게 도착하기 전에 블러가 준비된다.

**서버측 사전처리 없이 클라이언트에서 실시간으로 하려면 지연이 반드시 필요하다**
— 이게 이 시스템이 존재하는 이유이자 논문의 주장이다.
헤비 VLM으로 앞부분을 미리 훑는 경로는 **제품 경로가 아니라 실험 경로**다 — 아래
[실험 경로](#실험-경로--헤비-vlm-오프라인-채점)에서 별도로 다룬다.

> **검토 중 — 적응형 버퍼.** 지금 3초는 고정이지만, 분류 자체가 "콘텐츠마다 필요한 lookahead가
> 다르다"고 말하므로 버퍼 길이도 내용에 따라 바뀔 수 있다. 긴장이 쌓이는 구간은 늘리고 대화 장면은
> 줄이는 방식이다. 분류 주장이 서술에서 알고리즘이 되고 시청 품질 문제도 완화되지만, 링버퍼 길이를
> 동적으로 바꾸는 구현이라 **M1·M2 결과를 보고 판단한다.**

**3초는 임의의 숫자가 아니다.** [Time Buffers](https://arxiv.org/abs/2010.03016)가 약 2~3초 버퍼에서
탐지 정확도 향상(THUMOS'14 mAP +13.8%p, 300프레임 오프셋)을 보고했다. 선행 연구에서 유효성이 확인된 구간을 채택한다.

### 2. lookahead 요구량 기준 분류

민감 콘텐츠를 "무엇인가"가 아니라 **"얼마나 미리 알아야 하는가"** 로 나눈다.
이 분류가 탐지 경로 배치를 결정하며, 프로젝트의 설계 주장이다.

이 축을 모달리티와 교차하면 버퍼가 필요한 칸이 하나뿐이라는 것이 드러난다.

| | 오디오 | 영상 |
|---|---|---|
| **예측 불가형** (버퍼 필요) | **점프 스케어** — 규칙기반 → YAMNet | — |
| **지속 상태형** (버퍼 불필요) | **사이렌** — YAMNet 기존 클래스에 임계값 | **유혈 · 거미 · 주사기** — CLIP zero-shot |

지속 상태형은 화면·소리가 수 초간 유지되므로 프레임 N을 탐지해 N+1을 가려도 늦지 않는다.
**서버측 사전처리 없이 클라이언트에서 실시간으로 개입한다는 전제 아래서, 지연 버퍼가 필요한 것은
예측 불가형뿐이다.** 따라서 **점프 스케어는 카테고리 하나가 아니라 시스템의 제약 조건을 정의하는
클래스**다. 카테고리 5종의 선정 근거와 이 2×2의 배치는
[제안서 부록 A](docs/proposal.md#부록--확장-카테고리-taxonomy)가 원본이다.

### 3. 저비용 카테고리 확장

카테고리별 파인튜닝 대신 CLIP zero-shot을 쓴다. 새 카테고리를 **재학습 없이** 추가할 수 있어
확장 비용이 거의 0에 가까워지고, 일정이 밀릴 때 "제일 먼저 자르는 항목"이 아니게 된다
— 배포 관점의 단서는 [사용 모델](#사용-모델)에 있다.
정확도가 부족한 카테고리 1개만 선별해 **보강 모델**로 채운다. 보강 모델의 종류는
실패한 카테고리에 맞춘다 — 거미·주사기처럼 **물체**면 YOLO 파인튜닝이 맞고, 유혈처럼
화면에 퍼진 **색·질감**이면 네모를 칠 대상이 아니므로 경량 이미지 분류기 파인튜닝이 맞다.
어느 카테고리가 부족한지는 **04단계 앞부분**의 카테고리별 정확도 측정에서 나오므로, 도구는 그때 정한다(09.20).

## 실험 경로 — 헤비 VLM 오프라인 채점

**제품에 통합하지 않는다.** GPT-4o·Gemini는 외부 API 호출이라 분석이 기기 밖으로 나가고,
이는 "클라이언트 실시간이 주장의 핵심"이라는 범위 선언과 정면으로 부딪힌다.
사용자가 영상을 열자마자 재생하는 일반적 시청 패턴에서 스캔이 재생을 따라잡지 못한다는
실용적 문제도 그대로 남는다.

**대신 05단계 비교 실험의 상한선 벤치마크로 남긴다(09.20 — 비교표가 05단계로 갔다).** 동일 평가셋을 오프라인으로 채점해
규칙기반 / 학습모델 / CLIP zero-shot과 나란히 놓는다. 오프라인 채점이라 제품 경로와 무관하므로
[밀리면 자르는 순서](#밀리면-자르는-순서)의 컷 대상도 아니다 — 다만 **마감이 다르다.**
11.05 발표는 E1으로 채우고(09.15 변경), 우리가 만든 셋을 놓는 3자 비교표와 GPT-4o 열은 **둘 다
05단계(11/30)**에서 함께 만들어 4자를 완성한다(09.20). CLIP zero-shot 열이 04단계 구현을 기다려야 해
11.19 이전에는 나오지 않기 때문이다. 오프라인 채점이라 열을 나중에 덧붙여도 표가 깨지지 않는다.
조건부 항목이 아니라 마감이 뒤인 항목이다.

이 결정의 원본은 [제안서 §2.3 비목표](docs/proposal.md#23-비목표)다.

## 관련 연구와 차별점

선행 조사 결과 **동일 조합을 다룬 연구는 없다.** 다만 개별 요소는 대부분 선례가 있으므로,
"우리가 처음 하는 일"이 아니라 **"따로 있던 것을 처음 잇는 구조"** 로 주장한다.

전체 조사 내역과 문헌 목록은 [docs/related-work.md](docs/related-work.md)에 있다.

### 지연 버퍼 기반 사전 차단 — PSE 연구에 선례 있음

가장 가까운 선행 계열이다. 광과민성 발작(PSE) 도메인에는 프레임 버퍼로 위험 자극을
사용자 도달 전에 완화하는 연구가 이미 있다.

- [Flikcer: A Chrome Extension to Resolve Online Epileptogenic Visual Content with Real-Time Luminance Frequency Analysis](https://arxiv.org/pdf/2108.09491) — 크롬 확장 + 실시간 영상 분석 + 발작 유발 콘텐츠 차단. **구조적으로 가장 가까움**
- [Parallel scheme for real-time detection of photosensitive seizures](https://www.sciencedirect.com/science/article/abs/pii/S0010482516000123) — 실시간 스트리밍 탐지, 8프레임 버퍼
- [A new adaptive temporal filter: Application to photosensitive seizure patients](https://pubmed.ncbi.nlm.nih.gov/11145469/) — 프레임 메모리 버퍼로 사전 감쇠
- [Evaluating Conformance of Video Safety Tools for Photosensitive Epilepsy](https://pmc.ncbi.nlm.nih.gov/articles/PMC12249941/) — 해당 도구군의 평가 프레임워크

| | PSE 연구 | 본 연구 |
|---|---|---|
| **버퍼의 역할** | **시간축 필터링** (플리커 평활화) | **사건 탐지 후 도달 전 차단** |
| 탐지 대상 | 저수준 신호 (휘도 주파수) | **의미론적 사건** (점프 스케어·유혈·거미) |
| 카테고리 | 단일 고정 | 다중 · zero-shot 확장 |
| 버퍼 크기 | ~8프레임 (약 0.3초) | 3초 |

버퍼 크기는 역할이 다른 결과일 뿐 차별점이 아니다 — 크기를 늘려서 되는 일이 아니라,
**저수준 신호 평활화가 아니라 의미론적 사건 탐지를 버퍼 안에서 수행한다는 점**이 다르다.

→ **버퍼를 쓴다는 사실은 새롭지 않다.** 다만 "의미론적 사건을 잡는다"도 새롭지 않다 — 아래를 본다.

### 버퍼 시간을 탐지에 활용 — online action detection에 선례 있음

**주장이 가장 크게 겹치는 계열이다.**

- [Online Action Detection in Streaming Videos with Time Buffers](https://arxiv.org/abs/2010.03016) (Zhang et al., 2020)
  — 라이브 스트리밍의 송출 지연으로 생기는 **버퍼 시간을 탐지에 활용하는 문제 설정**을 제안한다.
  실험 버퍼는 **약 2~3초**, THUMOS'14 기준 mAP **+13.8%p**(300프레임 오프셋에서 53.6 vs StartNet 39.8)
- [Real-time Online Video Detection with Temporal Smoothing Transformers (TeSTra)](https://arxiv.org/abs/2209.09236)
- [Online human action detection and anticipation in videos: A survey](https://www.sciencedirect.com/science/article/abs/pii/S0925231222003617)

이 계열은 **버퍼 안에서 의미론적 사건을 탐지한다.** PSE 비교표에서 "저수준 신호 vs 의미론적 사건"으로
갈라놓은 그쪽에 이미 서 있으므로, lookahead로 의미를 읽는다는 것만으로는 차별점이 되지 않는다.

| | Time Buffers (2020) | 본 연구 |
|---|---|---|
| **버퍼의 출처** | 라이브 방송에 **이미 존재하는** 송출 지연 | VOD에 **의도적으로 도입하는** 지연 |
| 카테고리별 lookahead 요구량 | **구분하지 않음** (균일 버퍼) | 예측 불가형 / 지속 상태형으로 분리 |
| 목적 | 탐지 정확도(mAP) | **사용자 도달 전 차단** |
| 실행 위치 | 언급 없음 (알고리즘 성능만) | **브라우저 클라이언트 실시간** |

→ **주장은 "버퍼 활용"이 아니라 "개입을 위해 없던 지연을 만들어낸 설계 결정"에 둔다.**
공짜로 있는 버퍼를 이용한 것과, 사용자에게 3초를 손해 보게 하면서까지 lookahead를 확보한 것은
설계 문제로서 다르다.

이 논문은 응용 예시로 "라이브 웹캐스트에서 NSFW가 탐지되면 실시간 red flag를 보낸다"를 들지만
**동기로만 언급하고 구현하지 않으며, red flag는 알림이지 차단이 아니다.**
본 연구는 그 자리를 구현하고 사용자 실험으로 검증한다.

### 점프 스케어 오디오 특징 — affective computing에 선례 있음

02단계에서 쓸 특징 설계는 이미 표준이다.

- [Affective Content Analysis in Comedy and Horror Videos by Audio Emotional Event Detection](https://ieeexplore.ieee.org/document/1521500/) — 공포 영상 오디오 감정 이벤트 탐지
- [Affective Video Retrieval: Violence Detection in Hollywood Movies](https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0078506) — **energy entropy 기반 급작스러운 큰 소리 측정**, **혈흔 탐지**가 표준 특징
- [Affective Video Content Analysis: A Multidisciplinary Insight](https://dl.acm.org/doi/10.1109/TAFFC.2017.2661284) — 서베이
- [Multi-modal learning for affective content analysis in movies](https://link.springer.com/article/10.1007/s11042-018-5662-9)

→ 검증된 특징을 재사용하는 것이므로 안전하나, **"우리가 처음 제안한다"고 쓰지 않는다.**
결정적 차이는 이 계열이 전부 **오프라인 분석·검색**이 목적이고 **재생 중 개입이 아니라는 점**이다.

### 트리거 워닝 브라우저 확장 — 상용 제품 있음

- [PhobiaBlocker](https://chromewebstore.google.com/detail/phobiablocker/gjgghmahciffkcelboddbmkjkjchjnfk) — 공포증 이미지·영상 블러. **주변 텍스트 NLP** 기반
- [Trigger Warning Extension](https://chromewebstore.google.com/detail/trigger-warning-extension/emlcofoghclkckaajlejfoegblhahoff) · [Youtube Trigger Warning](https://chromewebstore.google.com/detail/youtube-trigger-warning/dhaighcmggigocehbgigdbmgpkhcekgl?hl=en) · SKIP IT — **크라우드소싱 타임스탬프·메타데이터** 기반

→ **픽셀을 보지 않는다.** 라벨이 없는 영상에는 무력하고 실시간이 아니다.
심사에서 "이미 있는 것 아닌가"가 나올 지점이므로 관련연구에 선제적으로 명시한다.

**그 뒷단에 사람이 만든 점프 스케어 타임스탬프 DB가 있다** — 수천 편 규모이고
([근거](docs/related-work.md#33-점프-스케어-타임스탬프-데이터베이스--네-곳-규모가-크다)), 규모 자체가 수요의 증거다.
**그리고 등재된 작품에만 동작한다** — 이 프로젝트가 채우는 빈칸이 그 바깥, 등재되지 않은 임의 영상이다.

### 정리 — 무엇이 새로운가

| 주장 | 상태 |
|---|---|
| 지연 버퍼로 사전 차단 | ❌ PSE 연구에 선례 |
| 버퍼 시간을 탐지에 활용 | ❌ online action detection에 선례 |
| 버퍼 안에서 의미론적 사건 탐지 | ❌ 위와 동일 |
| 점프 스케어 오디오 특징 | ❌ affective computing에 선례 |
| 공포증 콘텐츠 블러 확장 | ❌ 상용 제품 존재 |
| 점프 스케어 시점 정보 제공 | ❌ 타임스탬프 DB 다수 존재 |
| **개입을 위해 없던 지연을 도입** | ✅ 기존 계열은 이미 있는 버퍼를 이용하거나 오프라인 분석 |
| **재생 중 개입 (online intervention)** | ✅ 기존 계열의 목적은 정확도·검색. Time Buffers도 NSFW 알림은 동기로만 언급하고 미구현 |
| **lookahead 요구량 기준 아키텍처 분류** | ✅ 선행 사례 확인되지 않음 |
| **점프 스케어 자동 탐지** | ✅ 현상 정의 문헌은 있으나(Acosta & Sears 2026) 자동 탐지 연구 미확인 |
| **등재되지 않은 임의 영상에서 동작** | ✅ 확인한 타임스탬프 DB·크라우드소싱 확장은 모두 사전 등재가 전제 |
| **의미론적 다중 카테고리 × 브라우저 내 실행 × zero-shot 확장의 조합** | ✅ 조합 자체가 공백 |

| **브라우저** | **CLIP ViT-B/32** (사전학습, ONNX) | ❌ | 유혈 · 주사기 · 거미 |
| **브라우저** | **보강 모델 1개** | ⭕ 파인튜닝 | **04단계 앞부분** 측정에서 부족한 카테고리가 **나올 때만**(그 단계 뒷부분에 만든다) |
| 실험 전용 | **GPT-4o / Gemini** | ❌ | [상한선 벤치마크](#실험-경로--헤비-vlm-오프라인-채점). 제품에 넣지 않는다 |

카테고리별 탐지 경로 배치의 원본은 [제안서 부록 A.2](docs/proposal.md#a2-카테고리-5종)다.

**왜 ViT-B/32인가** — B/16과 파라미터 수는 거의 같지만(비전 타워 약 88M) **입력 패치 수가 다르다.**
B/32는 7×7+1 = 50토큰, B/16은 14×14+1 = 197토큰으로 **약 4배**다. 어텐션·FFN이 통째로 그만큼
늘어나 B/16이면 1~2fps 샘플링 목표를 못 맞춘다. L/14는 타워 자체가 약 304M으로 더 위다.

**텍스트 타워는 배포하지 않는다** — **04단계 튜닝으로 프롬프트가 확정된 뒤에는** 텍스트 임베딩을 오프라인에서 뽑아
작은 행렬로 싣고 **비전 타워만 확장에 넣는다.** 설치 크기가 절반 이하로 줄어든다.
대신 새 카테고리 추가가 "런타임 프롬프트 교체"가 아니라 **"임베딩 재계산 후 확장 갱신"** 이 되므로,
[핵심 아이디어 3](#3-저비용-카테고리-확장)의 저비용은 *학습 비용이 0*이라는 뜻이지
*무배포*라는 뜻이 아니다.
**확정 전까지는** 프롬프트가 04단계 앙상블·임계값 튜닝에서 계속 바뀌므로, 개발 중에는
텍스트 타워를 함께 싣거나 임베딩을 갈아끼우는 경로를 둔다(03단계 ONNX 변환에서 처리).

**모델이 아닌 것** — 02단계 규칙(RMS · 상승 시간 `dRMS/dt` · 스펙트럼 플럭스 · 직전 정적 구간)과
시각 특징(히스토그램 차이로 컷 전환, 평균 밝기 변화, 프레임 차이로 움직임)은 신경망이 아니라
프레임 간 산술이다. **CLIP과 같은 1~2fps 샘플링에서 계산하는 것을 전제로** 비용이 거의 없다 —
720p 전 프레임에 돌리면 무시할 수 없다.

**런타임** — ONNX Runtime Web · WebGPU, 미지원 시 WASM 폴백 · 추론은 Web Worker에서 돌려 재생을 막지 않는다.

## 클립 추출 규칙

**오탐과 미탐 중 미탐이 더 나쁘다.** 트리거 워닝은 놓치면 목적 자체가 무너지므로
recall을 우선해 임계값을 잡고, 오탐은 사용자 민감도 설정으로 조절한다.
이 입장이 평가 지표 해석과 04단계 민감도 슬라이더 기본값을 함께 결정한다.

평가셋은 영상당 5분 이내 클립으로 자른다. 최종 규모는 50~80개이고(**규모 확장은 05단계에
여유가 있을 때 한다 — 09.21~22. 04단계 앞부분 7일에는 확장 카테고리 라벨링만으로도 물량이 차고,
05단계에도 여유가 없으면 44개 안에서 라벨링한 규모로 고정한다**. 11.05 발표용 축소셋은 15~20개,
09.13 기준 44개 절단 완료),
80개 기준 물량(5분 × 80개 = 400분)은 감당되지만,
**어디를 자르느냐가 숫자의 신뢰도를 결정한다.**

점프 스케어 구간을 알고 그 주변을 잘라내면 클립 내 점프 스케어 밀도가 실제 영상보다 훨씬 높아지고,
**precision이 낙관적으로 나온다.** 오탐률은 "점프 스케어가 없는 시간"이 충분해야 측정되는데
그 시간이 잘려나가기 때문이다.

- 클립 경계를 **사건 기준으로 잡지 않는다.** 무작위 오프셋으로 자른다
- **점프 스케어가 하나도 없는 대조 클립을 30% 이상 섞는다.** 이게 없으면 05단계 precision 숫자를 방어할 수 없다.
  **대조 클립은 전체 개수 안에서 채운다** — 위에 얹는 것이 아니다.
  80개 기준이면 사건 포함 클립이 56개 이하가 되며 라벨링 총량은 늘지 않는다.
  평가셋 규모가 줄어도 **비율은 그대로 지킨다** — 어기면 정밀도 숫자를 쓸 수 없다
- 위 규칙을 01단계 라벨 기준 문서에 함께 박아둔다

```javascript
const c = document.createElement('canvas');
c.width = 320; c.height = 180;
c.getContext('2d').drawImage(v, 0, 0, 320, 180);
console.log('pixel:', c.toDataURL().length > 1000);

const ac = new AudioContext();

ac.createMediaElementSource(v).connect(an);
an.connect(ac.destination);
setTimeout(() => {
  const d = new Uint8Array(an.frequencyBinCount);

```

## 인터페이스 계약

탐지기 → 재생기. 이 배열 하나가 전부다.

```javascript
[
  { time: 13.42, category: "jumpscare", confidence: 0.87, duration: 1.5, source: "rule" },          // 순간 사건 + 꼬리 1.5초
  { time: 48.10, category: "siren",     confidence: 0.64, duration: 3.5, source: "yamnet" },        // 사이렌 2.0초 + 꼬리 1.5초
  { time: 91.20, category: "blood",     confidence: 0.71, duration: 2.0, source: "clip-zeroshot" }  // 유혈 0.5초 + 꼬리 1.5초
]
```

`source` — 어떤 모델이 탐지했는지 기록해두면 05단계 카테고리별·모델별 성능표 집계가 쉬워진다.

`duration` — 블러를 유지할 시간(초). **사건이 끝난 뒤 1.5초를 더 덮는다** — 탐지기가 사건 길이를 알면
`길이 + 1.5`, 모르면 `1.5`. 블러는 `time`에서 시작해 `time + duration`까지 걸린다.

> **왜 「기본 지속 시간」이 아니라 「꼬리」인가.** 블러는 사건 **시작**(`time`)부터 걸리는데
> [라벨 기준 §2](docs/labeling-guide.md#2-무엇을-1건으로-세는가)의 병합 창은 앞 사건의 **끝**(`offset`)에서 1.5초를 잰다.
> 둘을 같은 단위로 맞추려면 블러가 사건 끝 뒤로 1.5초를 덮어야 한다. 「기본 1.5초」로 두면 순간 사건인
> 점프 스케어에서만 맞고, 수 초씩 지속되는 사이렌·유혈·거미·주사기에서는 끝나는 프레임에 블러가 풀려
> **라벨은 1건인데 개입은 두 번**이 된다. UX로도 사이렌이 멎는 그 순간에 가림이 풀리면 가린 의미가 없다.
>
> **출처** — 1.5초는 PoC가 점프 스케어로 데모를 돌린 값이다(`poc/delay-playback.js:204` `scheduleBlur(video.currentTime, 1.5)`,
> `:223` `blurNow(dur = 1.5)`). 지속 카테고리에서는 아직 검증되지 않았고, 짧게 느껴지면 **꼬리 길이만** 조정한다.
> 구간 정의(`time`부터 `time + duration`까지)는 제품 코드에서도 참이다 — `extension/src/player.js:85`
> `if (mediaTime <= t.time + t.duration) return t;`
>
> **⚠ 라벨링을 시작한 뒤에는 꼬리 길이를 바꾸지 않는다.** 병합 창과 같은 값이라, 2.0초로 올리면 지금 2건으로 센 것
> 중 일부가 1건이 되어야 하고 이미 찍은 라벨을 다시 봐야 한다. 바꿔야 할 이유가 생기면 라벨을 다시 보는 비용과
> 함께 판단하고, **여섯 자리를 같이 고친다** — 이 계약 · [라벨 기준 §2](docs/labeling-guide.md#2-무엇을-1건으로-세는가) ·
> `eval/labels.py`의 `MERGE_GAP` · [제3자 안내 §5](docs/labeling-guide-3rd-party.md) ·
> 계약을 다시 적은 예시 둘(`docs/proposal.md` · `extension/README.md`). 예시를 찾을 때는 값이 아니라
> 개념으로 훑는다 — `git grep -n 'duration: [0-9]'`.

| **CLIP zero-shot 정밀도** — 붉은 조명을 피로 잡는 식의 오탐. [UnsafeBench](https://arxiv.org/pdf/2405.03486) 기준 경량 zero-shot VLM의 F1이 0.55 안팎, 최고치(GPT-4V)도 0.709 | 높음 | 04단계 목표를 **F1 0.6대**로 잡는다. 프롬프트 앙상블·임계값 튜닝. 논문을 결과 독립적으로 프레이밍해 수치가 나빠도 기여가 남게 함 |
| **라벨링 물량** — 영상 50~80개 멀티카테고리 타임스탬프를 1명이 담당. 순수 시청만 8~13시간, 구간 라벨링은 그 2~3배 | 높음 | **영상 길이 상한(5분 이내 클립)** 을 미리 고정. 초과 시 개수 하향. **09.20~21에 단계를 갈랐다** — 점프 스케어 20클립은 03단계(10.22 완료), 확장 카테고리 라벨링은 04단계 앞부분, 규모 확장 50~80개는 **05단계에 여유가 있을 때**(없으면 44개로 고정) |
| **평가셋 편향** — 사건 주변만 잘라내면 점프 스케어 밀도가 과장돼 precision이 낙관적으로 나옴 | 높음 | [클립 추출 규칙](#클립-추출-규칙) — 무작위 오프셋 절단 + 대조 클립 30% 이상 |
| **CLIP 브라우저 추론 속도** — WebGPU에서는 1~2fps 여유, WASM 폴백은 프레임당 수백 ms | 중간 | 03단계에 WASM 폴백 동작 정의 포함. 초과 시 **프레임 샘플링 fps 하향**(1~2fps → 0.5fps) 또는 **동시 판정 카테고리 수 축소** — 컷 목록에 있는 항목을 폴백으로 지정하지 않는다 |
| **CLIP은 단일 프레임 모델** — 시간축 사건인 점프 스케어에는 기여하지 않음 | 낮음 (설계상 의도) | 점프 스케어는 오디오 규칙 + YAMNet 담당. lookahead 분류가 이미 이 경계를 반영 |
| **공개 정답지가 전부 영화 기반** — Where's the Jump·LIRIS-ACCEDE 모두 범위 선언의 DRM 제외에 걸려 평가셋으로 사용 불가 | 낮음 | 라벨 기준 정의·특징 검증용으로만 사용. 평가셋은 직접 라벨링한다 — [docs/related-work.md §3.5](docs/related-work.md#35-결론--공개-데이터셋의-역할) |

## 협업 규칙

- `main` 직접 푸시 금지. feature 브랜치 → PR → 리뷰 1인 → merge.
- **코드 작업은 시작할 때 Draft PR을 먼저 열고 assignee를 단다.** 누가 무엇을 잡았는지 보여야 겹치지 않는다.
  커밋이 하나도 없으면 PR을 만들 수 없으므로 빈 커밋으로 연다 — `git commit --allow-empty -m "작업 시작"`.
  끝나면 Ready for review로 전환한다. 문서 수정 같은 단발 변경은 예외.
- **논의는 PR 한 곳에 모은다.** 이슈와 PR로 흩어지면 한쪽이 방치된다.
  이슈는 **진행 체크용으로만** 쓴다 — 단계·마감 단위의 할 일 목록이고, 그 안에서 논의하지 않는다.
- 브랜치명: `<타입>/<요약>` 예) `feat/data-loader`, `fix/plot-axis`
- 커밋 메시지: 한 줄 명령형. 예) `데이터 로더 추가`
- 비밀값(API 키, 계정 정보)은 커밋하지 않는다.
