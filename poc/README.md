# 00단계 PoC — 3초 지연 재생

`delay-playback.js`를 유튜브 영상 페이지 콘솔에 붙여넣으면 영상이 3초 늦게 재생되고,
그 사이 지연 전 오디오에서 점프 스케어 후보를 찾아 사용자 도달 전에 블러가 걸린다.

## 기술 전제 검증 (`verify-premises.js`)

DRM · 픽셀 접근 · 오디오 접근을 한 번에 재고 표로 찍는다. 영상 재생 중인 탭 콘솔에 붙여넣는다.

**대상 콘텐츠** — 유튜브 일반 업로드 영상. `전제 3종 통과`가 나와야 한다.

**경계 확인** — DRM이 실제로 막는 것을 보려면 Widevine 자산이 필요하다.
유튜브 영화·대여는 구매해야 하므로 공개 테스트 자산을 쓴다.

1. [Shaka Player 데모](https://shaka-player-demo.appspot.com/)를 연다
2. 상단 **`ALL CONTENT`** 탭을 누른다
3. 필터 드롭다운에서 **`Widevine DRM`** 을 고른다 (자산 31개로 좁혀진다)
4. **`Angel One (multicodec, multilingual, Widevine)`** 을 재생한다
5. 재생이 시작되면 스크립트를 붙여넣는다

`DRM: 보호됨`과 픽셀 차단이 나오면 범위 선언의 근거 화면이 된다.

오디오 검사는 `createMediaElementSource`를 호출해 그 페이지의 오디오 경로를 WebAudio로
바꾼다. 원복하려면 새로고침한다.

### 실측 (2026.09.08, macOS Chrome)

**① 대상 콘텐츠 — 유튜브 일반 업로드** (`youtube.com/watch?v=y4LuqvC7_dQ`, 960×720)

```
[verify] 전제 3종 통과 — 대상 콘텐츠
DRM        없음 (mediaKeys 없음 — 평문 재생)
픽셀       OK (비검정 샘플 58/58)
오디오      OK (0이 아닌 샘플 24/25 · 최대 RMS 0.1584)
```

**② DRM 경계 — Shaka `Angel One (multicodec, multilingual, Widevine)`** (768×576)

```
[verify] DRM 보호 콘텐츠 — 범위 선언대로 대상 외
DRM        보호됨
픽셀       검은 화면 (비검정 샘플 0/58)
오디오      OK (0이 아닌 샘플 24/25 · 최대 RMS 0.0675)
```

**②에서 예상과 다른 것이 둘 나왔다.**

1. **픽셀 차단이 taint가 아니다.** `drawImage`도 `toDataURL`도 예외를 던지지 않고
   **검은 프레임이 그려진다.** 보호된 프레임이 canvas 합성 대상이 아니기 때문으로 보인다.
   예외만 잡는 검사는 이 경계를 **통과로 오판한다** — 이 스크립트가 픽셀 내용까지 세는 이유다
2. **오디오는 차단되지 않았다.** Widevine 보호 재생인데도 `AnalyserNode`로 읽힌다.
   DRM 콘텐츠에서도 오디오 단독 탐지는 원리적으로 가능하고, 막히는 것은 화면 개입뿐이다

**일반화하지 않는다.** 자산 하나, 소프트웨어 Widevine 한 경로에서 관측한 결과다.
하드웨어 보안 복호(`HW_SECURE_ALL`)나 유튜브 영화에서는 오디오도 막힐 수 있다.
범위를 넓히려면 그 조건에서 다시 재야 한다.

### 기록

측정 후 `window.__sbVerifyResult`에 결과가 남는다. 콘솔 출력 블록을 그대로 제안서 §6 표와
PR 본문에 붙인다.

## 실행

1. Chrome에서 유튜브 **일반 업로드 영상**을 연다 (영화·대여는 EULA·DRM으로 막힌다 — 범위 선언 참고)
2. `⌥⌘J`로 콘솔을 연다
3. **처음이면 콘솔에 `allow pasting`을 먼저 입력한다** — Chrome이 self-XSS 방지로 붙여넣기를 막는다
4. `delay-playback.js` 전체를 붙여넣는다

```
scareblockDemo.stop()          원복
scareblockDemo.blurNow(1.5)    수동 블러 — 지금 소리 나는 장면을 도달 전에 가린다
scareblockDemo.stats()         버퍼·탐지·드롭 계측
```

Safari는 쓰지 않는다. 최종 산출물이 Chrome MV3 확장이라 검증 환경을 맞춘다.

## 실측 (2026-09-08, Big Buck Bunny 60fps)

| 항목 | 결과 |
|---|---|
| `drawImage(video)` | 오류 없음 |
| `canvas.toDataURL()` | **성공 — taint 없음.** 픽셀 접근 전제 확인 |
| 링버퍼 적재 | 4.5초에 64/70 슬롯 |
| 조회된 프레임의 지연 | **3.02초** (목표 3.00초) |
| 프레임 내용 | 231/231 샘플이 비검정 — 실제 화면이 들어옴 |
| `createMediaElementSource` | 예외 없음, `AudioContext.state = running` |
| 지연 전 RMS | 25/25 샘플이 0이 아님 (0.0039 ~ 0.0731). **오디오 접근 전제 확인** |

유튜브가 MSE(`blob:`)로 미디어를 붙이기 때문에 cross-origin taint가 걸리지 않는다는
README 「기술 전제」의 근거가 추론이 아니라 실측으로 확인됐다.

**화면 표시 경로는 미검증이다.** 검증 환경의 탭이 `document.hidden = true`라
`requestAnimationFrame`·`requestVideoFrameCallback`이 발화하지 않아, 적재·조회·오디오만
타이머로 우회 검증했다. 보이는 창에서의 부드러움은 사람이 직접 봐야 한다.
아래 드롭 계측도 같은 이유로 **아직 실측값이 없다** — 보이는 창에서 한 번 돌려야 채워진다.

## M1 계측 — 확장으로 넘겼다

**PoC와 확장은 이제 다른 것을 재는 도구다.** M1 판정은 확장(`extension/`)이 맡는다.
이 PoC는 **「3초 지연이 무엇인지 보여주는 것」** 이 역할이고, 기본값도 그래서 640×360@20fps로
가볍게 둔다. 두 곳의 숫자가 다르면 **M1에 관한 한 확장 쪽이 기준**이다.

아래 세 카운터의 정의는 확장이 그대로 물려받았으므로 기록으로 남긴다. `stats()`가 센다.

| 필드 | 뜻 | 세는 법 |
|---|---|---|
| `적재누락프레임` | 콜백이 못 따라가 **링버퍼가 못 본** 원본 프레임 | `meta.presentedFrames` 델타가 2 이상 |
| `렌더끊김` | 출력 캔버스 rAF 간격이 32 ms(60Hz 두 프레임)를 넘은 횟수 | `performance.now()` 델타 |
| `디코더드롭` | 브라우저가 디코드 단계에서 버린 프레임 (시작 시점 대비 증분) | `getVideoPlaybackQuality().droppedVideoFrames` |

메모리는 슬롯 수(`⌈지연×적재fps⌉ + 10`)와 해상도로 정해진다.

| 설정 | 슬롯 | 슬롯당 | 합계 |
|---|---|---|---|
| 640×360 @ 20fps (현재) | 70 | 0.88 MB | **61.5 MB** |
| 1280×720 @ 20fps | 70 | 3.52 MB | **246 MB** |
| 1280×720 @ 60fps | 190 | 3.52 MB | **668 MB** |
| 1920×1080 @ 20fps | 70 | 7.91 MB | **554 MB** |

01단계의 실제 쟁점은 1080p가 아니라 **720p에서 적재를 20fps로 갈지 60fps로 갈지**다
(246 MB vs 668 MB). 1080p는 어느 쪽이든 링버퍼 방식으로는 무리다.

## 지연 재생 실측 (2026.09.10, macOS Chrome, 보이는 창)

`document.hidden` 때문에 미검증으로 남겼던 **화면 표시 경로를 사람이 직접 확인했다.**

| 항목 | 결과 |
|---|---|
| 3초 지연 육안 확인 | ✅ 진행바 시각과 화면 내용이 3초 차 |
| 오디오·영상 립싱크 | ✅ 입 모양이 맞음 |
| **재실행 후 립싱크** | ✅ **#5 리뷰 ①(재실행 시 오디오 미지연) 수정이 검증됨** |
| `stop()` 원복 | ✅ 캔버스 제거, 원래 플레이어 복귀 |

**드롭 계측** — 104.1초 재생, 640×360@20fps, 70슬롯(61.5 MB)

```
적재누락프레임: 2      렌더끊김: 1      디코더드롭: 0      렌더fps: 60
```

`렌더fps 60`은 정상이다. **출력 rAF 루프가 60 Hz로 돌고 내용만 20 fps로 갱신**된다.

**640×360@20fps는 여유롭다.** 104초에 드롭이 사실상 0이다.
720p는 픽셀이 4배(246 MB)라 이 결과로 M1을 보장할 수는 없으나,
**여기서 드롭이 났다면 720p는 확정적으로 불가능**했으므로 유의미한 하한이다.

### 720p 자원 측정 (2026.09.11) — 01단계 설계 결정

`Big Buck Bunny 60fps 4K`(`aqz-KE-bpKQ`)를 **720p60으로 고정**하고 상수만 바꿔 세 번 쟀다.
원본이 60fps여야 캡처율 상한을 볼 수 있고, 해상도가 진짜 720p여야 디코드 비용이 맞다.

| | 640×360@20fps | 1280×720@20fps | **1280×720@40fps** |
|---|---|---|---|
| 경과 | 69.2초 | 74.6초 | 68.1초 |
| 적재누락 | 1240 (**17.9/s**) | 1384 (**18.6/s**) | 1239 (**18.2/s**) |
| 콜백 실제 속도 | 42.1 fps | 41.4 fps | 41.8 fps |
| 렌더끊김 | 0 | 0 | 0 |
| 디코더드롭 | 0 | 2 | 0 |
| 렌더fps | 60 | 60 | 60 |
| 슬롯 · 메모리(이론) | 70 · 61.5 MB | 70 · 246 MB | 130 · **457 MB** |

**적재누락이 해상도에도 캡처율에도 변하지 않는다** (17.9 / 18.6 / 18.2, 차이 4% 이내).
처음 720p에서 1384를 보고 해상도 탓으로 읽었으나, 같은 영상에서 640×360으로
되돌린 대조 측정이 그 해석을 뒤집었다.

> ### ⚠️ 이 절의 원인 분석은 틀렸다 (2026.09.11 정정)
>
> 위 불변성을 **"60fps 원본에서 rVFC가 42fps로만 배달되는 브라우저 쪽 한계"** 로 읽었다.
> **아니었다.** 원인은 우리가 HUD에서 **프레임마다 `getVideoPlaybackQuality()`를
> 부른 것**이었다. 그 호출이 rVFC 콜백을 굶겨 초당 18장을 놓치고 있었다.
>
> 확장에서 그 호출을 4Hz로 낮추자 **초당 18.8 → 0.1로 188배 줄었다**
> (`extension/` 실측, 77.7초에 6장).
>
> 다섯 번 측정이 전부 17.9~19.1로 일정했던 것은 브라우저 한계라서가 아니라
> **우리 고정 오버헤드였기 때문**이다. 해상도를 4배로 올려도 변하지 않는다는
> 사실을 「통제 불가」의 증거로 읽었는데, 정확히 거꾸로 읽은 것이다.
> **불변성은 외부 제약의 증거가 아니라 내부 상수의 증거였다.**
>
> 아래 「결정 셋」 중 ①②는 그대로 유효하다 — 해상도·캡처율 비교는 같은
> 오버헤드 위에서 이뤄졌으므로 상대 비교가 성립한다. **③은 근거를 잃었다.**

`디코더드롭 2 → 0`은 개선이 아니라 측정 노이즈다. 그 규모에서 2는 유의미하지 않다.

### 결정 셋

**① 720p를 채택한다.** 640×360 대비 추가 비용이 관측되지 않았다.

**② 캡처는 40fps로 올린다.** 20fps에서 40fps로 가는 비용도 관측되지 않았고,
「오디오는 매끄러운데 영상만 끊긴다」는 한계가 절반으로 준다. 메모리 457 MB가 대가다.

**③ 60fps 캡처는 당분간 하지 않는다.** ~~콜백이 42fps로만 돌아 원리적으로 불가능하다~~
— 위 정정대로 **이 근거는 틀렸다.** 오버헤드를 걷어내니 콜백은 60fps로 돈다.

남는 이유는 **메모리뿐이다.** 60fps면 190슬롯 668 MB이고, 40fps의 457 MB도 이미 적지 않다.
캡처율을 올려 얻는 것(시청 매끄러움)보다 저사양 기기에서 잃는 것이 커 보인다.
**열어둔 선택지로 두고 01단계 메모리 실측 뒤에 다시 판단한다.**

**실제 메모리는 재지 못했다.** 위 값은 `슬롯 × W × H × 4`의 이론치다.
맥 Chrome의 작업 관리자는 `창` 메뉴에 있고, 캔버스 백킹 스토어는 JS 힙 밖이라
`performance.memory`로는 잡히지 않는다.

**재는 법은 정해 뒀다** — 작업 관리자의 **GPU 프로세스 메모리**를 확장 켠 상태와 끈 상태로
재고 그 차이를 링버퍼 몫으로 본다. 457 MB가 이론치대로면 저사양 기기 제약이 실제로 걸리는
자리이고 40fps냐 60fps냐도 이 숫자로 갈리므로, **01단계에서 가장 먼저 잰다.**

### 메모리 실측 (2026.09.24) — 캔버스는 GPU 메모리에 잡힌다

같은 영상(`aqz-KE-bpKQ`, 720p60 고정)에서 확장을 껐을 때와 켰을 때를 Chrome 작업 관리자로 쟀다.
1280×720 @40fps · 130슬롯 구성이다.

| | 기준선 (확장 OFF) | 확장 ON | 차이 |
|---|---|---|---|
| 탭 메모리 | 342 MB | 429 MB | **+87 MB** |
| GPU 메모리 | 33.1 MB | 521 MB | **+488 MB** |
| | | **합계** | **+575 MB** |

**이론치 457 MB**(130 × 1280 × 720 × 4)와 **GPU 증가분 488 MB**의 차이는 **6.8%** 다.
`슬롯 × W × H × 4` 계산이 실제와 거의 맞는다.

**캔버스 백킹 스토어는 JS 힙이 아니라 GPU 메모리에 있다.** 그래서 `performance.memory`로는
잡히지 않고 작업 관리자의 **GPU 메모리 열**을 봐야 한다. 앞서 720p 측정에서 실제 메모리를
재지 못한 이유가 이것이었다.

탭 메모리도 87 MB 늘었다. 캔버스 객체·링버퍼 배열 등 JS 쪽 부대비용으로 보인다.

### 60fps를 포기한 판단이 여기서 확정된다

[#21](https://github.com/scareblock/scareblock/pull/21)에서 60fps를 **메모리 사유로** 보류했다.
실측 비율을 60fps(190슬롯)에 적용하면 이렇게 된다.

| | 40fps (실측) | 60fps (추정) |
|---|---|---|
| 슬롯 | 130 | 190 |
| 이론치 | 457 MB | 668 MB |
| GPU (×1.068) | 488 MB | **≈ 713 MB** |
| 탭 (비례) | 87 MB | ≈ 127 MB |
| **합계** | **575 MB** | **≈ 840 MB** |

**840 MB는 통합 그래픽·저사양 기기에서 감당하기 어렵다.** 40fps 유지가 맞다.

### 기동 시 끊김에 대한 가설

M1 측정에서 끊김 14건이 전부 기동 직후에 몰렸다(0~69초 12건, 이후 0건).
**488 MB의 GPU 텍스처를 한꺼번에 할당하는 것**이 그 구간과 겹친다.
확인된 인과는 아니지만, 슬롯을 나눠 할당하면 완화되는지는 볼 만하다.

### 렌더 시간 실측 (2026.09.24) — `--render-s = 0.017`

1280×720 @40fps, 93.4초, 트리거 827프레임분. `scareblock.renderTiming()`.

| | p50 | p90 | max | n |
|---|---|---|---|---|
| 블러 프레임 draw | 0.1 ms | **0.2 ms** | 0.3 ms | 827 |
| 일반 프레임 draw | 0.0 ms | 0.1 ms | 0.3 ms | 4096 |
| 블러 프레임 간격 | 16.6 ms | 17.3 ms | **22.1 ms** | 827 |
| 일반 프레임 간격 | 16.7 ms | 17.3 ms | **114.1 ms** | 4096 |

평균 프레임 주기 16.69 ms · **`render_s = p90(블러 draw) + 프레임 주기 = 0.0169 s`**

**블러 비용은 0.1 ms다** — 프레임 예산 16.7 ms의 0.6%.

**GPU에서도 비싸지 않다.** `draw`는 CPU가 명령을 넣는 시간이라 GPU 완료를 포함하지
않는다. 그래서 프레임 간격을 함께 쟀고, p50·p90이 블러/일반 동일하다.
CPU 시간만 봤으면 「GPU에서 비쌀 수도」라는 의심이 남았을 자리다.

**`render_s`의 거의 전부가 한 프레임 주기다.** 블러는 0.2 ms고 나머지 16.69 ms는
다음 합성까지 기다리는 시간이다. **줄일 수 있는 값이 아니라 구조적 하한**이며,
어떤 구현이어도 최소 한 프레임은 기다린다.

E1에 넣으면 `탐지 지연 0.005 + 렌더 0.017 = 0.022초`로, lookahead 0.5초에도 여유가 크다.

**이 값은 이 기기 기준이다** (맥, 720p@40fps, 60 Hz 디스플레이). 120 Hz 화면이면
프레임 주기가 절반이라 `render_s`도 절반이 된다. 저사양 기기에서는 반대로 늘 수 있다.

### 계측을 기본에서 빼야 했다 — 세 번째 함정

이 계측을 **상시 켜둔 채로** M1을 다시 재니 통과하지 않았다.

| | 경과 | 끊김 | 분당 | M1 |
|---|---|---|---|---|
| 계측 ON | 390 s | 21 | 3.23 | **false** |
| 계측 OFF | — | — | — | **true** |

계측 ON 구간을 쪼개면 0~217초 분당 2.49, **217~390초 분당 4.16**으로 오히려 늘어,
기동 과도 현상으로 설명되지 않았다.

**프레임당 `performance.now()` 2회와 배열 쓰기 2회가 원인이다.** 비용 자체는 마이크로초
단위지만, 렌더 루프의 뜨거운 경로에 분기와 메서드 호출이 끼면 최적화가 풀릴 수 있다.

**재현은 각 1회씩이다.** 끊김이 실행마다 0.77~10.41/분으로 흔들리는 것을 아는 이상
인과를 확정할 수는 없다. 다만 **M1 통과 이후 확장에서 바뀐 기능 코드가 이 계측뿐**이었고,
기본 경로에서 빼는 판단은 어느 쪽이든 옳다 — 데모 빌드에 계측 비용이 있어서는 안 된다.

지금은 `scareblock.measure(true)`로 켤 때만 표본을 모으고, 꺼져 있으면 프레임당
불리언 검사 둘만 남는다.

> **같은 함정 세 번**
> 1. `getVideoPlaybackQuality()` 프레임당 호출 → 적재누락 초당 18.8 (4 Hz로 낮추니 0.1)
> 2. `DelayNode.maxDelayTime` 오독 → `NaN` 전파로 검은 화면
> 3. **렌더 시간 계측 상시 켜둠 → M1 판정 뒤집힘**
>
> 셋 다 `node --check`와 순수 로직 테스트로는 안 잡힌다. **브라우저 실행 경로를
> 건드리는 변경은 실기에서 M1을 다시 재야 한다.**

### 114 ms 스톨은 블러 탓이 아니다

일반 프레임 간격의 max가 114.1 ms인데 **블러 프레임은 22.1 ms가 최대**다.
끊김이 블러와 무관하다는 뜻이고, 위 「기동 시 끊김에 대한 가설」(GPU 텍스처 488 MB 일괄 할당)과 맞는다.

### 탐지 오탐 — 104초에 9건

점프 스케어가 없는 일반 영상에서 9건이 걸렸다. **정밀도가 사실상 0이다.**

관측된 한 건의 수치로 원인이 설명된다.

```
[scareblock] 점프 스케어 후보 t=159.74s rms=0.176 (직전 중앙값 0.027, 최근 최댓값 0.1815)
```

| 조건 | 계산 | 결과 |
|---|---|---|
| `median < peak * 0.15` | `0.027 < 0.0272` | 간신히 통과 |
| `cur > median * 5` | `0.176 > 0.135` | 통과 |
| `cur > peak * 0.3` | `0.176 > 0.054` | 여유롭게 통과 |

즉 **"말하다 잠깐 쉬고 다시 말하기"** 가 전부 걸린다. 임계값을 올리면 조용해지지만
(`0.08 / 8 / 0.6` 정도) 영상마다 다시 맞춰야 하고 진짜 사건도 놓치기 시작한다.

**이것이 02단계가 필요한 이유의 첫 실측 증거다.** 지금까지 "RMS 급등만으로는 부족하다"는
추측이었고 이제 숫자가 있다. 그리고 **왜 상승 기울기(`dRMS/dt`)가 필요한지**도 여기서 나온다 —
말소리는 천천히 커지고 점프 스케어는 2~100 ms 만에 커진다. **크기로는 못 가르고 기울기로 갈린다.**
02단계 규칙 기반 탐지기가 넘어야 할 기준선이 이 숫자다.

## 알려진 한계 (01단계에서 해결)

캔버스로 다시 그리므로 **전체화면·자막·화질설정·재생컨트롤이 동작하지 않고**,
해상도가 640×360으로 고정된다. **표시 프레임률도 `CAPTURE_FPS`(20fps)로 떨어져,
원본이 60fps여도 사용자가 보는 것은 20fps다** — 오디오는 매끄러운데 영상만 끊긴다.
일시정지·배속은 대응하지 않는다.
시크는 **뒤로 갈 때 적재가 멈추지 않게 복구만** 한다(`t < lastCap`이면 기준을 푼다).
복구가 없으면 이전 위치를 다시 지날 때까지 링버퍼가 영구히 멈춘다.

이는 README 위험 표 첫 줄(「지연 재생 시청 품질」)이 말하는 그 문제이고,
M1의 정량 기준(720p 무드롭 60초)이 이 PoC가 아니라 01단계 구현을 겨눈 이유다.

## 탐지 규칙에 대해

`DETECT` 경로는 "직전 1초가 조용했고 지금 RMS가 급등"이라는 **조악한 규칙**이다.
02단계의 규칙 기반 탐지기(정적 → 음량 급등 + 저음 럼블)를 대신하지 않는다.
제안서에서 "지연 버퍼가 있으면 도달 전 개입이 가능하다"를 보이는 용도로만 쓴다.

임계값은 전부 **최근 최댓값 대비 상대비**다(`QUIET_OF_PEAK`·`SURGE_OF_QUIET`·`SURGE_OF_PEAK`).
`AnalyserNode`가 element volume **뒤**를 듣기 때문에, 절대값을 쓰면 영상이 아니라
유튜브 볼륨 슬라이더에 종속된다 — 볼륨을 낮추면 급등을 못 잡고, 높이면 "조용" 조건이
깨져서 역시 못 잡는다.

**상승 시간(rise time)은 아직 못 본다.** 50 ms 간격 RMS 샘플링으로는 놀람 반사 문헌이
말하는 2~100 ms 상승 시간 차이를 분해할 수 없다. 02단계에서 `dRMS/dt`를 규칙에 넣기로
하면 샘플 간격도 함께 내려야 한다.
