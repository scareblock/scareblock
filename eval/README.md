# 평가 하니스

#14의 **E1 — lookahead 시간별 성능 곡선**을 내기 위한 오프라인 파이프라인이다.
발표(11.05)의 E1 결과가 이 출력 하나로 채워진다. 09.14 논문은 이 설계를 「실험 설계」로 적었다.

브라우저가 아니라 파이썬으로 둔 이유는 실험을 수십 번 돌려야 하기 때문이다.
PoC(`poc/delay-playback.js`)는 데모·계측용이고, 여기는 평가용이다.

## 무엇을 재는가

**적시성** — 탐지가 맞았는지가 아니라 **사용자에게 도달하기 전에 개입이 준비됐는지**다.

사건마다 **탐지 지연**을 기록하고, lookahead `L`을 쓸어가며 `지연 ≤ L`인 비율을 센다.

```
지연 = (규칙이 확신에 이른 시각) − (라벨 onset) + (블러 렌더링 시간)
```

**기준점은 라벨 onset이다.** 탐지기가 되짚어 만든 추정 onset을 쓰면 탐지기를 자기
자신과 비교하게 되고, 지연이 "되짚기가 멈춘 거리"로 바뀐다(#19 리뷰 🔴1).
사용자가 노출되는 시점은 라벨 onset이다.

**확신 시각은 분석 창의 끝이다**(`Features.t_ready`). 창 시작을 쓰면 25 ms 창 안의
자극을 창이 시작할 때 이미 알았다는 뜻이 되어 지연이 음수로 나온다.

**렌더링 시간은 상수 하나**다(`evaluate.RENDER_S`, `--render-s`). M1 실측 뒤 값만
넣으면 표가 다시 나온다. 측정 전이므로 기본값은 0이다.

### 헤드라인은 탐지 지연 분포다 (2026.09.13 결정)

**E1의 주 결과는 사건별 탐지 지연의 분포 — 중앙값 · p90 · 최댓값이다.** 표 머리줄 바로 아래에
나오고, 「필요한 지연량」은 p90(+렌더링 시간)으로 읽는다.

```
**탐지 지연** (라벨 onset → 확신, 매칭 N건) — 중앙값 … s · p90 … s · 최댓값 … s
→ 필요한 지연량(p90 기준) ≈ … s (렌더링 시간 미측정)
```

**lookahead 0에서 적시성이 0인 것은 결과가 아니다.** 확신 시각을 분석 창의 끝으로 정의했으므로
**라벨 onset이 상승 시작점이면** 지연이 음수가 될 수 없고, 어떤 탐지기를 넣어도 0이 나온다 — 헤드라인으로
쓰면 동어반복이다.

**다만 라벨 onset 기준으로는 음수가 될 수 있다.** 매칭은 탐지기가 되짚은 onset과 ±0.5초로 붙으므로,
주석자가 정점 근처를 찍어 라벨 onset이 늦으면 `확신 − 라벨 onset`이 음수가 된다(#33 리뷰 🔴1). 그러면
lookahead 0 열도 0이 아니게 되고 p90이 음수로 나온다. 그래서 헤드라인은 **음수 지연 건수를 따로 알리고**
(`⚠ 음수 지연 N건 — 라벨 onset을 확인한다`), **필요한 지연량은 0 아래로 내리지 않는다.**
렌더링 시간을 넣으면 `≈ 0.660 s (렌더링 0.20 s 포함)`처럼 **이미 더한 값**으로 적는다.
측정의 초점은 3초라는 초기값이 과잉인지다. p90이 1초 근처면 **"필요한 양은 3초가 아니라 X초"** 로 쓴다.

**적시성 ≤ recall은 항등식이다.** 적시성의 분자는 매칭된 사건 중에서만 세므로
`적시성 = recall × 잡은 것 중 제때`다. 못 잡은 사건도 「늦음」으로 들어간다. 그래서 표에
**「잡은 것 중 제때」(`in_time / TP`)** 열을 따로 둔다 — 「잡았는가」와 「잡은 것이 제때인가」가 갈린다.
이 열을 lookahead별로 읽으면 곧 탐지 지연 분포의 **누적 분포(CDF)** 라, 곡선과 헤드라인이 같은 것을 가리킨다.

## 입력

**라벨** — `docs/labeling-guide.md` §1 스키마 CSV를 그대로 읽는다.

```csv
video_id,clip_id,clip_offset,onset,offset,category,ambiguous,annotator,note
aqz-KE-bpKQ,c007,742.0,46.33,47.10,jumpscare,false,B,문 쾅 + 화면 컷
```

`note`는 있으면 읽고 없으면 무시한다. `duration`은 받지 않고 `offset − onset`으로 계산한다.

**평가 분모는 라벨이 아니라 클립 목록이다.** 대조 클립은 사건이 없는 것이 정상이라
라벨 행을 하나도 남기지 않는다. 라벨에서 클립 목록을 역산하면 **대조 클립이 평가에서
통째로 빠지고 오탐이 한 건도 세지지 않는다**(#19 리뷰 🔴1). `--clips clips.csv`로
명세를 주면 그것이 분모가 되고, 없으면 wav 디렉터리 전체를 쓴다.

```
라벨이 분모 (고치기 전)   라벨 있는 클립만 → precision 1.000 (대조 클립의 오탐이 안 보임)
명세가 분모 (지금)       명세 전체       → precision 0.625 (오탐 3건이 세짐)
```

`clip_id` 열만 요구하고 나머지 열은 무시한다 — 명세가 열을 늘려도 안 깨진다.

**실제 평가 집합은 명세 ∩ wav다.** 거기서 벗어난 것은 전부 알리고 뺀다.

| 어긋남 | 그냥 두면 | 처리 |
|---|---|---|
| 명세 밖 `clip_id`의 **라벨** (오타 등) | 참 사건이 분모에서 사라져 recall이 부풀고, 대조 비율 분모까지 오염된다 | 경고 후 제외 (#26 재리뷰 🔴1) |
| 명세에 있는데 **wav 없음** | 표가 조용히 줄어든다 | 경고 · 머리줄 `클립 25/26개 ⚠️` |
| wav는 있는데 **명세 밖** | 평가에 섞인다 | 경고 후 제외 |

**대조 비율은 평가된 클립으로 잰다.** 명세 전체로 재면 유일한 대조 클립의 wav가 없을 때
경고가 침묵한다(#26 재리뷰 🟡2). 30% 기준이 지키려는 것은 출력된 표의 precision이다.

**표 머리줄이 표의 성격을 적는다** — `주석자 B · 클립 25/26개`. `--clips` 없이 돌리면
`클립 25개 (명세 없음)`이 된다. 폴백은 wav 목록이 곧 분모라 개수 비교가 무의미하기 때문이다
(#26 재리뷰 🟡3·🟡4). 경고는 stderr로 가고 표만 논문에 옮겨지므로, 그 사실들이 표 안에 있어야 한다.

**주석자는 한 명만 쓴다.** 이중 라벨링(`labeling-guide` §6) CSV를 그대로 넣으면 같은
사건이 두 번 세지고, 매칭이 1:1이라 둘 중 하나가 자동으로 미탐이 된다(#19 리뷰 🔴2).
섞여 있으면 가장 많이 단 사람을 골라 알리고, `--annotator`로 바꾼다.
**고른 사람이 분모의 일부만 라벨링했으면 경고한다** — §6의 이중 라벨링은 10~15%만 겹치므로
`--annotator A`로 돌리면 나머지가 전부 대조 클립으로 세져 비율이 80%대로 뛰고 30% 검사를
넘어간다. 평가가 가장 망가진 상태에서 대조 비율 경고가 조용해지는 자리다(#26 리뷰 🟡1).
**두 주석자를 함께 읽는 것은 κ 계산뿐이다.**

**클립 경계를 넘어 매칭하지 않는다.** 모든 클립의 시간축이 0에서 시작하므로 합쳐서
매칭하면 클립 A의 탐지가 클립 B의 라벨에 붙어 TP가 부푼다(#19 리뷰 🔴2).
`Detection.clip_id`를 매칭 조건에 넣어 막는다.

**클립 명세** — `clips.csv`. `eval/clipcut.py`가 낸다.

```csv
clip_id,video_id,clip_offset,duration_s,source_class,url,seed,clip_s,margin_s,video_duration_s
c001,f7jkZXvaB4g,4347.76,300.11,scare,https://www.youtube.com/watch?v=f7jkZXvaB4g,20260912,300.0,60.0,5743.0
```

**이 파일이 「무엇을 봤나」의 유일한 근거다.** 라벨은 「무엇이 있었나」만 말하므로,
`labeling-guide §4`의 **대조 클립(라벨 0건)** 은 라벨 파일에 아무 흔적도 남기지 않는다.
따라서 클립 목록을 라벨에서 역산하면(`by_clip(truth)`) 대조 클립이 분모에서 사라지고,
대조 비율을 30%로 맞춰도 `control_ratio`가 0%로 나와 **경고가 거꾸로 뜬다.**
오탐을 세야 할 클립이 분석에서 통째로 빠지는 것도 같은 뿌리다(#19 재리뷰 🔴1).

`seed`·`clip_s`·`margin_s`·`video_duration_s`는 **오프셋이 무작위였다는 것을 증명하는 값**이다.
이 넷이 있으면 `draw_offsets`를 그대로 재실행해 같은 오프셋을 다시 뽑을 수 있다 —
심사에서 "클립을 어떻게 골랐나"에 답해야 하는 자리다(#24 리뷰 🔴2).

**오디오** — `<clip_id>.wav` 파일들이 든 디렉터리. mp4에서 뽑으려면:

```bash
ffmpeg -i c007.mp4 -ac 1 -ar 16000 -vn c007.wav
```

## 실행

```bash
pip install -r eval/requirements.txt
python3 -m eval.e1 --labels labels.csv --audio _local/wav --clips _local/clips/clips.csv
```

임계값은 `detect.Params`의 필드가 그대로 인자다 — `--surge-of-quiet` · `--quiet-of-peak` ·
`--surge-of-peak` · `--drms-min` · `--cooldown-s` · `--silence-floor` · `--backtrack-max-s`.
기본값과 다른 값은 표 아래 「동작점:」 줄에 남는다. 기울기 조건은 `--drms-min 값`으로 켠다(기본 0은 끔).
M1 실측 뒤 렌더링 시간을 반영하려면 `--render-s 값`.

**동작점 고르기 — 라벨을 보기 전에.** `--rate-sweep`은 분당 발화율 표만 내고 `--labels`를 주면 거부한다
([labeling-guide §4](../docs/labeling-guide.md)).

```bash
python3 -m eval.e1 --audio _local/dataset/wav --clips _local/dataset/clips.csv \
  --rate-sweep surge_of_quiet=5,20,35,60
```

44클립·212.7분(2026.09.15)에서 6.37 · 2.19 · 1.18 · 0.49건/분이고, 같은 표가
[labeling-guide §4](../docs/labeling-guide.md#4-클립-수집과-절단)에 실려 있다.
6.53 · 2.36 · 1.27 · 0.51은 **33클립 165분에서 잰 옛 값**으로, §4에 경위로 남아 있다.

**데이터 없이 파이프라인만 점검:**

```bash
python3 -m eval.e1 --selftest
```

## 자체 점검 결과 (2026.09.12, 합성 오디오 클립 2개 × 30초)

| lookahead | 적시성 | precision | recall |
|---|---|---|---|
| 0.0s | **0.000** | 1.000 | 1.000 |
| 0.5s | **1.000** | 1.000 | 1.000 |
| 3.0s | **1.000** | 1.000 | 1.000 |

2 ms 상승 점프 스케어 5건을 모두 잡고, **1.5초에 걸쳐 서서히 커지는 크레셴도는 잡지 않았다**
(`labeling-guide` §5의 「넣지 않는 것」과 일치). 라벨 onset 기준 지연은 다섯 건 모두 0.005초
— 분석 창 25 ms의 절반 수준으로, 사실상 **한 창 안에서 확신했다**는 뜻이다.

클립을 2개로 둔 이유는 **클립 간 교차 매칭이 단일 클립에서는 드러나지 않기** 때문이다.
`c001@12.0`과 `c002@12.4`를 일부러 허용오차(±0.5초) 안에 배치했고, 자체 점검이
"다른 클립·0.05초 차 쌍은 0건, `clip_id`를 무시하면 1건"을 함께 검사한다.

**합성 데이터라 이상적인 값이다.** 실제 영상은 바닥 소음이 있고 상승이 완만해
지연이 더 길게 나온다. 이 표는 파이프라인이 도는지를 보인 것이지 결과가 아니다.
**「0.5초면 충분하다」는 이 표로 말할 수 없다** — 지연이 창 하나 크기라 0.5초든 3초든
전부 1.000이다. 실제 클립에서만 갈린다.

## 모듈

| 파일 | 역할 |
|---|---|
| `labels.py` | §1 스키마 로드·검증, 대조 클립 비율 |
| `features.py` | RMS · **dRMS/dt** · 스펙트럼 플럭스 · 직전 정적 · 감쇠 최댓값 |
| `detect.py` | 규칙 탐지기. 확신 시각·onset 추정·`clip_id`를 기록한다 |
| `evaluate.py` | 같은 클립 안 onset ±0.5초 매칭(§6), P/R/F1 + 적시성 + 잡은 것 중 제때 + 탐지 지연 분포 요약 |
| `e1.py` | lookahead 스윕, 표 출력, 발화율 스윕(`--rate-sweep`), 자체 점검 |
| `yamnet.py` | 사전학습 YAMNet 클래스 점수 → 탐지 (11.05 조건부 열, 학습 없음). 모델 만들기는 [yamnet-setup](../docs/yamnet-setup.md) |
| `iaa.py` | 주석자 간 일치도 — 사건 매칭 κ · 100 ms 구간 κ · PSA를 한 번에 ([labeling-guide §6](../docs/labeling-guide.md#6-주석자-간-일치도)) |

**홉은 10 ms다.** PoC의 50 ms로는 놀람 반사 문헌이 말하는 2~100 ms 상승 시간을
분해할 수 없었다(`poc/README.md` 탐지 절).

**onset 되짚기에는 1초 상한이 있다**(`Params.backtrack_max_s`). 바닥이 조용해지지 않는
구간에서는 `t=0`까지 내려가 추정이 무의미해진다(#19 리뷰 🟡3). 상한에 걸린 건수를
리포트 머리줄에 낸다 — 되짚기가 실패하는 빈도 자체가 데이터 특성을 알려준다.
되짚은 onset은 **진단용**이고 적시성 계산에는 들어가지 않는다.

**정규화는 dtype 범위로 한다.** 클립의 실제 최댓값으로 나누면 조용한 클립일수록 크게
증폭돼, 절대값인 `silence_floor`가 클립마다 다른 음압을 가리킨다(#19 리뷰 🟡5).

**`dRMS/dt`는 후방차분이다.** `np.gradient`는 중심차분이라 `drms[i]`가 `rms[i+1]`에
의존하는데, 확신 시각은 `t_ready(i)`로 적힌다 — **아직 나오지 않은 프레임으로 확신했다고
기록**하는 셈이다(#19 리뷰 🟡3). 창 시작/끝 문제와 같은 종류다.

**겹치는 라벨은 검사에서 걸린다.** 병합 검사의 하한이 0이면 겹치거나 완전히 똑같은 두 행이
그냥 통과한다(#19 리뷰 🟡4). 다만 검사는 **주석자별로** 본다 — 이중 라벨링에서 두 사람이
같은 사건을 각자 찍는 것은 위반이 아니다.

**임계값은 나머지 전부 상대값이다** — 최근 최댓값 대비로 잡아 볼륨 설정에 종속되지 않게 했다.
PoC에서 절대 임계값이 볼륨 슬라이더에 종속됐던 문제(#5 리뷰 🟡3)를 같은 방식으로 피한다.

## 범위 밖

학습 모델(YAMNet), CLIP zero-shot, 멀티모달 융합은 여기 없다. 09.14 논문은
규칙 기반 베이스라인까지만 담는다.
