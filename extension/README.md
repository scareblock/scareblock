# scareblock 크롬 확장 (02단계)

**탐지는 규칙 기반이다** — `eval/detect.py`를 그대로 옮긴 `detector-rule.js`가 지연 전
소리를 듣고, 점프 스케어를 찾으면 화면이 거기 닿기 전에 가린다(M2). 동작점은 #35 사전
등록값 `surge_of_quiet = 20`이다. 01단계의 가짜 탐지기는 `config.js`의 `DETECTOR: 'fake'`로
남겨 두었다 — M1을 다시 잴 때 10초 주기가 필요하다.

## 설치

1. `chrome://extensions` 접속
2. 오른쪽 위 **개발자 모드** 켜기
3. **압축해제된 확장 프로그램을 로드** → 이 `extension/` 폴더 선택
4. 유튜브 영상 페이지로 이동 — **홈·검색에서 클릭해 들어가도 된다**

> 콘텐츠 스크립트는 매치되는 URL로 **문서가 로드될 때만** 주입된다. 유튜브는 SPA라
> 홈에서 영상을 클릭하면 문서 로드가 없으므로, `/watch`로만 매치하면 실사용 진입
> 경로 대부분에서 확장이 아예 붙지 않는다. 그래서 `youtube.com` 전체로 매치하고
> `main.js`의 `boot()`에서 `location.pathname === '/watch'`로 걸러낸다. 진입 경로가
> 어디든 `yt-navigate-finish` 한 자리로 모인다.

영상이 3초 늦게 재생되고, 정적 뒤 소리가 급등하면 블러가 걸린다.
콘솔에 `규칙 탐지 #n onset=… fire=… (지금 …)` 가 찍히고, 실제 블러는
그 3초 뒤에 나타난다. **그 간격이 이 시스템의 존재 이유다.**

## 콘솔

```js
scareblock.stats()          // 계측값 + M1 판정
scareblock.measure(true)    // 렌더 계측 켜기 (기본 꺼짐)
scareblock.renderTiming()   // 렌더 시간 — eval 의 --render-s 용
scareblock.blurNow()        // 지금 장면을 도달 전에 가린다
scareblock.detections()     // 지금까지 낸 탐지 수
scareblock.setSurge(5)      // 데모용 동작점 전환 (기본 20 = E1 동작점)
scareblock.stop()           // 원복
```

## 동작점과 데모 (`setSurge`)

기본 동작점은 **E1과 같은 `surge_of_quiet = 20`** 이다 — 직전 1초 중앙값보다 20배 넘게 커져야 울린다.
이 값은 #35에서 라벨을 보기 전에 정했고 E1 보고값이라 바꾸지 않는다.

**바탕 소리가 깔린 영상에서는 20배에 닿지 않는다.** 2026.10.07, 프레디의 피자가게 데스신 모음
(`qMHZj5zxX0A`, 108초, 사용자가 센 점프 스케어 8개)에서 탐지가 0건이었다. 탐지기가 듣는 RMS를
10 ms마다 기록해 보니 영상 전체에서 가장 큰 급등이 **×8.5**였다. 사람 귀에는 조용해도 환풍기·배경음이
깔려 직전 1초 중앙값이 0.02–0.05에 머물고, 「쾅」이 커도 배율은 3–8배에 그친다.
같은 기록으로 다시 계산하면 ×10·×15에서도 0건, **×5에서 4건**(21.7 · 35.7 · 57.6 · 79.7초)이다.

그래서 데모에서는 동작점을 콘솔에서 바꿔 **두 값을 나란히 보여준다.**

```js
scareblock.setSurge(5)    // 더 잡는다 — 대신 일반 장면에서도 9초에 한 번 울린다 (44클립 스윕 6.37건/분)
scareblock.setSurge(20)   // E1 동작점으로 되돌린다 — 27초에 한 번 (2.19건/분)
```

**5는 E1에 숫자가 있다.** 사전 등록한 민감도 부록(5 · 20 · 35 · 60)의 한 값이라, 데모에서 5를 써도
E1 밖의 값이 아니다(개발 B 확인, 10.07). 5일 때 **recall 66% · 공포 영상 6.1건/분 · 일반 영상 6.9건/분**.
그래서 데모에서 밝힐 것은 「**E1 보고값은 20, 데모는 5**」 한 줄이다.

**프레디 영상만의 일이 아니다.** E1에서 동작점 20이 잡은 27건은 급등 배수 중앙값 **40배**, 놓친 49건은
**6.5배**이고 놓친 49건 중 48건이 20배 미만이다. 배경음 때문에 20배에 못 닿는 것이 놓침의 거의 전부다.

「낮추면 잡지만 오탐이 는다」가 보여줄 내용이다. 오탐을 줄이는 다음 단계가 10.03 말소리 기각
(#35, 일반 영상 오탐 −63%)이다. **데모에서 5를 쓸 때는 E1과 다른 값이라고 밝힌다.**

## 렌더 시간 측정 (`--render-s`)

`eval/e1.py`의 적시성 계산은 **탐지 지연 + 렌더링 시간 ≤ lookahead** 로 판정한다.
렌더링 시간이 없으면 p90이 하한으로만 쓰인다. 그 값을 여기서 잰다.

```js
scareblock.measure(true)     // 켜고
// … 1분쯤 재생 …
scareblock.renderTiming()    // 읽는다
```

**기본은 꺼져 있다.** 프레임당 `performance.now()` 2회가 M1 측정에 섞이지 않게 하려는 것이고,
데모 경로에도 계측 비용이 있으면 안 된다. 켤 때 표본을 비우고 새로 모은다.

| 항목 | 뜻 |
|---|---|
| `블러프레임_draw_ms` | 블러를 걸고 그리는 데 걸린 시간 |
| `일반프레임_draw_ms` | 블러 없이 그린 시간 — 차이가 블러 비용이다 |
| `블러프레임_간격_ms` | 블러 프레임의 rAF 간격 — **블러가 비싸면 여기가 늘어난다** |
| `render_s(제안)` | `p90(블러 draw) + 한 프레임 주기` |

**draw 시간은 CPU가 명령을 넣는 시간이라 GPU 완료를 포함하지 않는다.** 그래서 프레임
간격을 함께 본다 — 블러가 GPU에서 비싸면 draw는 짧은데 간격이 늘어난다.

**`render_s(제안)`은 근사다.** 블러 결정은 그 프레임을 그리는 rAF 콜백 안에서 일어나고
픽셀은 다음 합성 시점에 보이므로 `draw + 한 프레임 주기`로 잡았다. 캔버스의 실제 제시
시각은 관측할 수 없다.

측정하려면 **트리거가 실제로 발동해야 한다.** 가짜 탐지기가 10초마다 내므로 1분쯤
재생하면 표본이 쌓인다. 빨리 모으려면 `scareblock.blurNow()`를 몇 번 부른다.

## M1 판정

`stats()`의 `M1통과`는 **`연속무드롭초 ≥ 60`** 일 때 `true`다.

`연속무드롭초`는 마지막 끊김·디코더드롭 이후 흐른 시간이다.
M1 기준이 *"60초 이상 유지"* 이므로 **누적 0이 아니라 연속 60초**가 맞다.
누적으로 재면 오래 돌릴수록 통과가 불가능해진다 — 10분 돌리면 그 안에
한 번만 끊겨도 실패로 잡힌다.

누적값과 `끊김_분당` · `누락_초당` 비율도 함께 낸다. 길이가 다른 측정을
비교하려면 비율이 필요하다.

**`적재누락`은 판정에 넣지 않는다. 사용자가 느끼지 못하는 내부 샘플링 손실**이기
때문이다. (한때 「해상도·캡처율과 무관한 상수라 통제 불가」로 설명했으나 틀렸다 —
프레임마다 부르던 `getVideoPlaybackQuality()`가 원인이었고, 4Hz로 낮추자 초당
18.8에서 0.1로 줄었다.) 근거는 [`poc/README.md`](../poc/README.md).

### 규칙 탐지기를 붙인 뒤 (2026.10.07)

풍선 터지는 소리 영상(`3yfUHUbQwKA`, 무음 사이 2~4초마다 「펑」), 1280×720@40fps, 동작점 20.
개발자도구는 별도 창, 측정은 `setTimeout(() => console.log(scareblock.stats()), 90000)`로 걸어 두고 손대지 않았다.

| | 경과 | 끊김 | 끊김_분당 | 디코더드롭 | 트리거 | 연속무드롭 | M1 |
|---|---|---|---|---|---|---|---|
| 콘솔 붙여 연 채 | 101.4 s | 18 | 10.65 | 3 | 29 | 0.3 s | false |
| 별도 창 · 직접 `stats()` | 104 s | 3 | 1.73 | 0 | 30 | 0.6 s | false |
| **별도 창 · 손대지 않음** | 94.9 s | 9 | 5.69 | 0 | 27 | **92.4 s** | **true** |

**통과한 회차의 끊김 9번은 전부 처음 2.5초 안이다**(94.9 − 92.4). 기동 시 끊김(`poc/README.md`
「기동 시 끊김에 대한 가설」)과 같은 자리이고, 그 뒤 92초 동안 탐지 27번·블러 27번 사이에 끊김이 0이다.

**탐지기 비용은 작다.** 같은 영상에서 콜백만 따로 30초 쟀다 — 2048 샘플마다 p50 0.2 ms ·
최대 0.8 ms, 메인 스레드의 약 0.4%, long task 0건.

**측정하는 손이 끊김을 만든다.** 두 번째 줄은 `stats()`를 치려고 창을 옮긴 0.6초 전에 끊겼다.
M1은 손대지 않는 방식으로 잰다. 콘솔을 페이지에 붙여 열면 탐지 로그(약 3초마다)가 렌더와
경쟁하는 것으로 보인다 — 첫 줄과 나머지의 차이지만 각 1회라 인과는 확정하지 않는다.
**`main`(가짜 탐지기)과의 대조는 하지 않았다** — 탐지가 도는 92초 동안 끊김이 0이라 가릴 것이 남지 않았다.

## 구조

| 파일 | 역할 |
|---|---|
| `config.js` | 상수. 값의 근거는 `poc/README.md` |
| `ringbuffer.js` | 프레임 링버퍼. 조회는 이분 탐색 O(log n) |
| `player.js` | 지연 재생·블러·음량 페이드다운. **계약 소비자** |
| `detector-rule.js` | 규칙 탐지기. **계약 생산자** — `eval/detect.py`와 같은 계산 |
| `detector-fake.js` | 10초마다 가짜 트리거 — M1 재측정용 (`DETECTOR: 'fake'`) |
| `main.js` | 조립 + 유튜브 SPA 네비게이션 대응 |

프레임당 비용이 계측을 실제로 망가뜨리므로(#21) **매 렌더 프레임 도는 두 조회는
둘 다 선형이 아니다** — 링버퍼는 이분 탐색이고, 트리거는 커서로 지난 것을 앞에서
잘라내 상수다. 시크·탭 복귀에서는 표시 시각이 뒤로 가므로 커서를 0으로 되돌린다.

```bash
node extension/test/ringbuffer.test.js   # 8/8 — 이분 탐색 = 선형 탐색
node extension/test/triggers.test.js     # 7/7 — 커서 조회 = 선형 탐색
```

**규칙 탐지기는 파이썬과 대조한다.** E1이 잰 탐지기와 데모의 탐지기가 같아야 E1의 숫자가
데모의 숫자다. 같은 wav를 양쪽에 넣어 발화 시각·onset을 10 ms 안에서 맞춘다.

```bash
python3 extension/test/rule-parity.py _local/dataset/wav/*.wav   # 3클립 52건 불일치 0 (2026.10.06)
```

브라우저는 48 kHz로 듣고 E1은 16 kHz wav를 썼다. 같은 3클립을 48 kHz로 올려 파이썬끼리
비교하면 52건이 전부 ±50 ms 안에 남고 1건이 더 걸린다 — 표본률 차이는 작다.

**미디어 시각 매핑.** 탐지기는 `ScriptProcessorNode`(2048 샘플)로 듣고, 첫 콜백의
`currentTime`을 원점으로 샘플 수를 센다. 5.000 s · 12.000 s에 급등을 넣은 합성 클립에서
onset이 4.968 s · 11.968 s로 나왔다 — **32 ms 일찍**, 블러가 조금 먼저 걸리는 안전한 쪽이다.
시크·버퍼링 복귀·배속 변경에서는 원점이 깨지므로 탐지기를 처음부터 다시 돌린다.

**재생기와 탐지기는 배열 하나로만 만난다.**

```js
[{ time: 13.42, category: "jumpscare", confidence: 0.87, duration: 1.5, source: "rule" }]  // 순간 사건 + 꼬리 1.5초 — 정의는 README 인터페이스 계약
```

`time`은 **라이브 mediaTime**이다. 화면은 그보다 `DELAY_SEC` 뒤를 보여주므로,
표시 시각이 그 구간에 들어올 때 블러가 걸린다.

## 설정값

`config.js`의 기본은 **1280×720 @ 40fps**(130슬롯 ≈ 457 MB)다.
**60fps 캡처도 가능하다** — 오버헤드를 걷어낸 뒤 rVFC는 60fps로 돈다. 그럼에도 40으로 두는
이유는 메모리뿐이다(190슬롯 ≈ 668 MB). 01단계 메모리 실측 뒤에 다시 판단하는 열어둔 선택지다.
측정 근거는 [`poc/README.md`](../poc/README.md) 「720p 자원 측정」.

## 오디오 재동기화

화면은 **mediaTime** 기준으로 `DELAY_SEC` 뒤를 보여주는데 `DelayNode`는 **벽시계**로
지연한다. 정상 재생에서는 둘이 같지만 세 곳에서 어긋난다. 뿌리가 하나라 한 곳에서 받는다.

| 상황 | 그냥 두면 | 처리 |
|---|---|---|
| **일시정지** | 멈춘 뒤에도 소리가 3초 더 난다 | `AudioContext.suspend()` — 지연선 내용이 보존된다 |
| **배속** | 2배속에서 소리가 1.5초 먼저 난다 | `delayTime = DELAY_SEC / rate` — 40 ms 음소거 뒤 교체 |
| **탭 숨김** | 돌아오면 과거 화면이 뜬다 | 링버퍼를 비운다 (시크와 같게) |

**일시정지에서 지연선을 버리면 안 된다.** 그 안에 든 3초는 **화면이 앞으로 보여줄
구간의 소리**다. 아직 한 번도 나간 적이 없다. 버리면 재개 후 3초가 무음이 된다.
그래서 드레인도 폐기도 아닌 **정지**가 답이다.

**배속은 램프로 바꿀 수 없다.** `delayTime`은 지연선의 **길이**라, 늘리면 읽기 지점이
되감겨 소리가 늘어지고 줄이면 건너뛴다(2배속 → 1배속에서 실측). 램프로는 그 점프를
숨길 수 없으므로 40 ms 음소거하고 무음 구간에서 갈아끼운다.

**음소거가 지우는 것은 점프의 클릭이고, 지연선에 든 내용은 아니다.** 배속을 되돌리면
`delayTime`이 1.5 → 3.0으로 뛰지만 지연선 안은 **2배속으로 흘러가던 때 녹음된 구간**
그대로다. 그래서 전환 직후 **이미 들은 말이 한 번 다시 들린다**(실측). 지연선이
1배속 입력으로 다시 차면서 그 뒤는 정상으로 돌아온다.

**고치지 않고 한계로 둔다.** 지연선을 비우면 재개 후 무음이 생기고, 두면 이 재청취가
남는다. 둘 다 대가가 있는데 **배속 전환은 드문 조작**이고 무음이 더 눈에 띈다. 일시정지
쪽 판단과 같은 이유다 — 지연선에 든 소리는 아직 한 번도 나간 적이 없어 버릴 수 없다.

**탭 숨김은 반대다.** rAF·rVFC가 멈춰 링버퍼만 비는데 영상과 오디오는 계속 간다.
돌아왔을 때 버퍼에 남은 건 낡은 프레임뿐이라 그대로 쓰면 과거 화면을 띄운다.
비우고 3초간 검은 화면으로 다시 채운다 — **검은 화면이 가장 안전한 상태**다.

## 설정 변경은 `SB.config` 한 곳으로만 받는다

`world: "MAIN"`이라 `chrome.*`를 못 쓴다. 04단계 설정 UI에는 ISOLATED 콘텐츠
스크립트와 `postMessage` 다리가 필요하다. **그 다리를 04단계에 가서 놓으면 늦다** —
그때는 설정을 읽는 코드가 재생기 안에 흩어진 뒤다.

그래서 규약을 지금 박아둔다. **설정 변경은 `SB.config` 갱신 한 곳으로만 받는다.**
재생기·탐지기는 `SB.config`를 읽을 뿐 어디서 왔는지 묻지 않는다. 다리를 놓을 때
건드릴 자리가 한 곳으로 끝난다.

## 알려진 한계 (01단계에서 남은 것)

- **전체화면·자막·화질설정이 동작하지 않는다** — 캔버스로 다시 그리기 때문
- **광고 미대응** — 광고 중에는 `<video>`가 광고라 링버퍼에 광고 프레임이 쌓인다.
  `#movie_player`의 `ad-showing` 클래스로 감지해 지연을 잠시 끄는 가드를 넣을 수 있다
- **배속을 되돌리면 이미 들은 말이 한 번 다시 들린다** — 지연선 길이만 갈아끼우고
  내용은 남기기 때문. 위 「오디오 재동기화」 참고. 비우는 쪽이 무음을 만들어 더 나쁘다
- 재생 중 화질 자동 전환 시 화면이 한 번 튈 수 있다 (확인 안 됨)
- MV3 `world: "MAIN"`이라 `chrome.*` API를 못 쓴다 (위 「설정 변경」 참고)
